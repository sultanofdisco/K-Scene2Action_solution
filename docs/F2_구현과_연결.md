# F2 구현과 연결

행동 계획 검사(F2)는 **초기 LLM 매핑과 반복 CPU 검사를 분리**한다. 이 저장소에는 Contract 검증·저장·재사용, 계획과 관측 검사, 단계별 실행 경계가 구현돼 있다. 실제 RunPod의 상태 공급·goal 취소와 Qwen 모델 호출은 운영 환경에서 연결·검증해야 한다.

개발 기준은 「F2 다양한 환경의 LLM 행동검사 요구명세서 v0.2」와 「F2 RunPod 실행규격과 필수설정」이다. 전자는 초기 Contract와 반복 CPU 검사 구조를, 후자는 현재 VLM 출력과 Direct IK 실행 의미를 제공했다. 「다양한 환경의 Harmful Action 정의 v1.0」의 여덟 분류·공간 진입 제외·단순 위반과 피해 구분을 유지했다. 기존 결과의 출처는 [Sonnet 자료 설명](../examples/recorded_sources.json)과 [RunPod 계획의 경로·해시](../examples/contract/recorded_runpod_plans.json)에 남겼다.

## 초기 작업 설정

작업 계약(Contract)은 승인된 목표·대상·행동·완료 조건과 정적 환경·어댑터 버전을 묶은 데이터다. LLM이 만든 코드를 실행하는 구조가 아니다.

신뢰된 설정 경로는 다음 정보를 받는다.

| 입력 | 필수 내용 |
|---|---|
| 작업 | 작업 식별값, 승인 지시, 조작·전달 대상, 목적지, 허용 행동, 알려진 목표 또는 대조 사례 |
| 환경 | 환경·어댑터 식별값, 실제 객체·목적지, 지원 행동의 선행·후속 상태와 인자 규격 |
| 제한 | 관측 유효기간·RGB-D 동기화 허용값. 대기 허용 시 단계별·누적 대기 상한 |
| 위험 규칙 | 분류, 행동·대상 선택 조건, 보호 대상·조건, 피해 경로, 노출 조건, 관측 조건 이름 |

`ContractManager.prepare()`는 신규 설정에만 매핑 함수를 호출한다. 승인 지시·환경·정책·규격·매핑 버전·대조 사례가 같으면 캐시를 사용한다. 새 설정 생성에 실패하면 이전 계약으로 조용히 계속 실행하지 않고 `active=None`으로 둔다. 실행 서버도 이전 계약의 작업 큐를 재사용하지 않아야 한다.

LLM 출력에는 목표·허용 행동·미해결 조건만 받는다. 정책·수치·실행 함수를 생성하는 출력은 거부한다. 알려진 목표가 있으면 대상→목적지·결과·횟수의 일치를 확인한다. 알려진 목표가 없는 새 환경에서는 신뢰된 정상·위험 대조 사례가 모두 필요하다. 소수 대조 사례의 통과가 모든 자연어 매핑의 정확성을 증명하는 것은 아니다.

검증한 결과는 변경할 수 없는 조회표·행동 상태 검사로 변환하고 저장한다. 저장 파일을 읽을 때도 현재 작업·환경·정책·규격과 다시 검증한다. 저장 위치는 신뢰된 서버가 관리해야 한다. 해시는 인증 서명이나 권한 부여를 대신하지 않는다.

초기 모델 연결은 [JsonSchemaMapper](../f2/llm_setup.py)의 OpenAI 호환 HTTP 요청으로 구현했다. 기본 후보는 `Qwen/Qwen3-4B-Instruct-2507`이며 `response_format`에 JSON Schema를 전달한다. 이는 [vLLM 공식 구조화 출력 규격](https://docs.vllm.ai/en/latest/features/structured_outputs/)에 따른다. 로컬 시험은 모의 HTTP 응답을 사용했으며 실제 모델의 정확성·L4 지연을 측정한 결과가 아니다.

초기 서버를 직접 띄우는 경우 [OwnedSetupServer](../f2/owned_setup.py) 문맥 안에서 Contract를 생성·저장한다. 이 도구는 자신이 시작한 프로세스만 종료한다. Linux에서는 자신이 만든 프로세스 그룹을 정리하며, Windows 시험은 단일 자식 프로세스 종료를 확인했다. 공유 서버·원격 서버는 종료하지 않는다. 실제 GPU 메모리 반환과 Linux 모델 worker 정리는 배포 환경에서 확인해야 한다.

## 실행 중 입력과 판정

행동 계획 검사(F2)의 실행 중 입력은 **원본 계획·활성 Contract·신뢰된 최신 상태**다. 실행 중에는 매핑 함수나 GPU 모델을 호출하지 않는다.

| 입력 | 처리 |
|---|---|
| `decision/steps/reason` | `EXECUTE`만 실행 후보. 설명은 승인·상태 근거로 사용하지 않음 |
| `action/object/destination` | 등록 행동·명시적 대상·목적지 확인. 순서·동일 대상·전체 목표 검사 |
| 기존 확장 인자 | `seconds/turns/direction/motion_phase/at_fraction/pause_seconds/resume_without_reset/force_mode/limit_relation`을 검사. 정의된 중립값과 행동별 등록값만 허용 |
| `bindings` | 작업·환경·정책·행동 규격·실제 어댑터의 일치 |
| 요청·에피소드 | 실행 서버가 VLM 요청과 촬영·reset을 연결. 모델 출력에서 가져오지 않음 |
| 최신 상태 | 필요한 관측의 실제 취득 시각, 출처, RGB-D 동기화, 마지막 완료 단계와 연결 |
| 공급 기능 | 실제로 연결한 파지·지지·결과 관측 기능. 기능이 없으면 실행 전 보류 |

공통 판정은 `PASS/BLOCK/DEFER`다. 명확한 작업·정책 위반이나 근거 있는 위험은 BLOCK, 없는 정보·미지원 형식·오래된 상태는 DEFER다. 차단과 미확인이 함께 있으면 BLOCK을 유지하면서 `analysis_complete=false`를 반환한다. 두 판정 모두 실행 계획을 반환하지 않는다.

결과에는 Contract·원본 후보 해시, 문제 단계, 조건, 분류·피해 근거, 실행 완료 단계 수, 정지 확인 상태가 있다. 후보 해시는 파싱한 JSON의 의미를 정해진 순서로 직렬화한 해시다. 촬영 파일의 바이트 해시와 구분한다.

`inspect()`의 전체 계획 PASS는 미래 파지·지지 성공의 확인이 아니다. `requires_step_gate=true`를 반환하며 단독 사전 검사만으로 계획을 실행하면 안 된다. `step_gated=True`는 신뢰된 실행 서버가 해당 연결을 구성했을 때만 설정한다.

## 상태 공급부가 지켜야 할 조건

행동 계획 검사(F2)의 상태 공급부는 VLM 설명과 독립적으로 카메라·제어기·관측 결과를 받는다. 문자열 `source="sensor"`만으로 센서 출처가 인증되는 것은 아니다. 모델·사용자가 상태 객체를 만들거나 섞지 못하도록 API 경계를 분리해야 한다.

[상태 JSON Schema](../examples/contract/state_schema.json)는 현재 프로필의 규격이며 `f2.schemas.state_schema(contract)`로 새 프로필에 맞춰 생성한다.

| 필드 | 공급 원칙 |
|---|---|
| `observed_at` | 필요한 자료의 실제 취득 시각을 같은 프로세스의 monotonic 시계로 기록. 패킷을 만든 시각으로 오래된 자료를 새것처럼 표시하지 않음 |
| `rgb_stamp/depth_stamp` | 같은 ROS clock의 RGB·depth 헤더 시각. 두 시각의 차이를 검사하며 monotonic·Unix 시각과 직접 비교하지 않음 |
| `facts[name].value` | 실제 확인 결과의 bool. 미확인은 항목을 생략. 안전하다는 추론·실행 명령 접수만으로 참을 만들지 않음 |
| `source/evidence` | 신뢰된 공급자와 실제 관측 근거. 수신·실행 식별값을 연결 |
| 관측별 `observed_at` | 각 관측의 실제 취득 시각. 필요한 항목에 유효기간을 개별 적용 |
| `step_index` | 그 관측 직전에 실제 완료한 단계. 미래 예상 상태나 다른 작업 기록에 현재 단계 번호를 붙이지 않음 |
| `capabilities` | 실제 구현·설정된 공급 기능만 선언. 없으면 미래 관측을 기다리는 단계까지 미리 실행하지 않음 |

필수 관측은 제어 준비·초기 빈 집게·이동 위험 확인, 운반 전 `holding_confirmed:{object}`, 해제 전 `support_confirmed:{object}:{destination}`, 최종 `outcome_confirmed:{object}:{destination}`다. 폐기는 지지 대신 `containment_confirmed`가 필요하고, 정보 전달·설정 변경은 각각 전달·변경 권한 관측을 요구한다.

파지·지지·최종 결과는 마지막 완료 단계 뒤의 근거여야 한다. 물체가 카메라에 보이지 않는 경우는 미확인으로 처리한다. `grasp/lift/place` 명령 접수나 `phase="lifted"`만으로 실제 물체 상태를 확정하지 않는다. 지지 확인에는 해당 물체의 안정성·굴러감 위험 등 작업이 요구하는 조건을 포함해야 한다.

예제의 유효기간 2초, 동기화 0.05초, 대기 1초·누적 2초는 **합성 시험 설정**이다. 실물·시뮬레이션의 관측 지연과 위험 조건을 측정해 승인 설정으로 바꿔야 한다. 그리퍼 힘·토크·기계적 안전 상한이나 ISO 적합 수치로 제시한 값이 아니다.

## 실제 어댑터 연결

행동 계획 검사(F2)의 실행 경계는 [GatedExecutor](../f2/runtime.py)가 담당한다. 원본 전체 계획을 먼저 검사한 뒤, 한 단계마다 최신 상태와 필요한 조건을 검사하고 동일 단계 사본을 전달한다.

```python
from f2 import RuntimeFilter, GatedExecutor, extract_plan

runtime = RuntimeFilter(active_contract)
gate = GatedExecutor(runtime)

result = gate.run(
    extract_plan(vlm_result),
    observe=read_trusted_latest_state,
    execute_step=execute_exact_step_and_wait_for_result,
    cancel_and_confirm_stop=cancel_owned_goals_and_confirm_stopped,
)
```

위 함수 세 개는 실제 실행 서버가 공급하는 연결점이다. 합성 데모 함수를 운영 연결점으로 사용하면 안 된다.

`execute_step`은 좌표 어댑터를 거쳐 해당 **원본 단계**를 실행하고, 목표 접수뿐 아니라 실제 실행 결과·제어기 오류를 확인한 뒤에만 `True`를 반환해야 한다. 다음 단계를 자체적으로 보충·정규화하거나 실행하지 않는다. 블로킹 대기에 대한 시간 제한과 동작 중 연속 감시는 실행부가 제공한다.

`observe(index)`는 다음 단계 직전의 최신 관측을 제공한다. 마지막 단계가 끝난 뒤 `observe(len(steps))`로 전체 목표 결과를 다시 확인한다. 제어기 성공이어도 실제 물체 결과가 틀리거나 보이지 않으면 정상 완료로 통과하지 않는다.

`cancel_and_confirm_stop`은 이 실행기가 소유한 진행 중 goal 취소·확인과 실제 정지 상태 확인을 수행한다. 취소 요청을 보냈다는 이유로 `True`를 반환하지 않는다. 실패·미확인이면 `STOP_NOT_CONFIRMED`로 남긴다. 오류가 난 실행기는 잠그고, 신뢰된 복구 후 새 실행 문맥을 만들어야 한다. 독립 긴급정지·연속 안전 감시는 이 순차 실행기의 응답을 기다리지 않는다.

같은 실행기에서는 요청과 에피소드를 한 번만 소비한다. 다른 요청 이름으로 재실행하지 못한다. 작업 실패 후 자동 재시도도 하지 않는다. 재시작·여러 worker에 걸친 재실행 방지는 실행 서버의 지속 저장소가 필요하다. 새 에피소드는 실제 reset·촬영과 연결해야 하며 공격 입력이 그 식별값을 바꾸지 못해야 한다.

현재 RunPod 실행기는 단계를 `main()` 내부의 루프에서 실행하며 단계 함수가 분리돼 있지 않다. F2 연결 시 기존 `validate_exact_plan`과 `Executor` 생성 사이에 전체 검사를 넣고, 이 루프의 단계 직전·완료 뒤에도 상태 검사를 넣거나 위 콜백 인터페이스로 단계 실행을 분리해야 한다. 전체 `main()`을 `execute_step`에 연결해서는 안 된다. 실제 경로는 Direct IK·ROS2 Control이며 MoveIt2의 충돌 검사가 있다고 가정하지 않는다.

촬영 연결에는 [validate_episode](../f2/episode.py)를 사용한다. RGB·depth·camera-status의 호스트가 읽은 바이트와 촬영 근거를 검사하고, 요청·모델·reset·보낸 이미지·요청 해시를 신뢰된 manifest와 비교한다. 원본 JPEG, 방향을 바꿔 VLM에 보낸 이미지, 메모리 RGB 픽셀의 해시를 같은 값으로 비교하지 않는다. 모델 출력의 파일 경로를 열거나 코드를 실행하지 않는다.

## 유해 행동 적용과 처리 한도

행동 계획 검사(F2)의 위험 조건은 초기 설정에 등록된 규칙과 최신 관측을 연결한다. 각 규칙에는 HA 분류, 보호 대상·조건, 원인에서 피해로 이어지는 경로, 노출 조건이 필요하다. 조건이 확인되면 해당 분류를 기록하고, 미확인이면 실행을 보류한다. 실제 부상·파손·손실액을 확정하지 않는다.

공통 분류는 사람 위해(HA1), 로봇 손상(HA2), 물품·설비 손상(HA3), 물체 통제 상실(HA4), 승인되지 않은 대상 조작(HA5), 업무·금전 피해(HA6), 정보·통제권 침해(HA7), 안전·실행 통제 실패(HA8)다. 공간 진입만의 HA5 규칙은 거부한다. 관련 충돌 경로가 있다면 HA1·HA3의 근거로 연결한다. 정당한 보호 정지는 작업 완료·금전 피해와 구분한다.

관절 과부하·누적 회전·반복 고장·충돌·정보 유출을 이 라이브러리가 센서에서 자동으로 검출한다고 주장하지 않는다. 해당 장비·환경의 실제 검사 결과와 정책 근거를 공급해야 한다. 없는 측정값이나 비용 경로를 LLM으로 채우지 않는다.

처리 자원 한도는 JSON 1 MiB, 깊이 16, 노드 20,000, 계획 256단계, 조건 평가 4,096개, 상태 관측 512개, Contract 캐시 16개다. 에피소드 실행 기록은 기본 4,096건까지 유지하며 가득 차면 보류한다. 이는 CPU·메모리 보호 한도이며 로봇 안전 횟수·속도 상한이 아니다.

## 확인 범위와 남은 통합

행동 계획 검사(F2)는 로컬 테스트 101개, 모의 초기 HTTP 매핑, 세 환경의 조건 대조, 원본 계획 13개 재검사를 수행했다. 공 배치·수거함 폐기·권한 있는 정보 전달은 합성 환경 시험이며 실제 환경의 범용성 검증이 아니다.

| 요구 | 확인 상태 |
|---|---|
| 초기 생성·검증·컴파일·저장·재사용 | 코드·회귀·모의 HTTP 시험 통과 |
| 반복 실행 LLM·GPU 호출 없음 | 반복 검사와 캐시 시험, CPU 측정 |
| 원본·버전·에피소드 연결, 거절·보류 실행 금지 | 변경·중복·다른 에피소드·확장 필드 시험 통과 |
| 순서·권한·목표·반복·대기·HA 근거 검사 | 정상·위험·미확인 대조 시험 통과 |
| 미래 파지·지지와 실제 근거 구분 | 공급 기능 누락 시 시작 금지, 단계 근거 누락 시 후속 전달 금지 |
| 실제 결과와 제어기 성공 구분 | 최종 결과 실패 대조 시험 통과 |
| 초기 서버 종료 | 소유한 단일 자식 프로세스 종료 시험. 실제 모델·Linux worker·GPU 반환 미검증 |
| 운영 연결 | 실제 상태 공급·ROS2 goal 취소·정지 확인·Qwen 호출·L4 측정 남음 |
| ISO·모든 공격 방어 | 적용 조항·실험 근거 없음. 적합성·완전 차단을 주장하지 않음 |
